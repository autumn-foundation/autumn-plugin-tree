# Ship a disclosure list that becomes a tree

Autumn should ship two hierarchy widgets, not one. The first is a **navigation disclosure list**: nested `<ul>` of real links, `<details>`/`<summary>` toggles, `aria-current="page"`, and **never `role="tree"`**. It covers docs sidebars and site menus, which is what most "tree" requests are, and it works fully without JavaScript. The second is a **`tree` widget pack** for selection and explorer work: file pickers, folder choosers and checkbox scopes. Its server output is the same no-JS disclosure baseline. On `autumn:init` the pack's script upgrades it into an APG tree: `li role="treeitem"` named by `aria-labelledby`, nested `ul role="group"`, **declared `aria-level`/`aria-setsize`/`aria-posinset` on every item**, a roving tabindex, `aria-selected` for single select, and `aria-checked` (including `mixed`) for checkbox trees. Native inputs stay in the DOM as the form-submission source of truth. This split follows the APG's own advice that "the disclosure pattern is better suited for most web sites" ([APG Navigation Treeview](https://www.w3.org/WAI/ARIA/apg/patterns/treeview/examples/treeview-navigation/)). It also follows the field lessons GitHub published after shipping its file tree: declared levels, label-span naming and roving focus were each needed to make screen readers behave ([GitHub Blog](https://github.blog/engineering/user-experience/considerations-for-making-a-tree-view-component-accessible/)). Lazy children load as htmx fragments swapped into the child group, with a plain-link fallback. The server computes tri-state and normalizes cascades on submit. The CSP posture is no `style=`, no `hx-on`, no trigger filter expressions, and depth and node budgets on rendering. One finding is specific to Autumn: the shared keyboard core already counts `[role=treeitem]` as a roving item, but as written it would arrow into collapsed branches and it ignores Ctrl. The tree needs a small core fix plus a pack-side handler for Left, Right and `*`.

## The APG contract is small, but three details decide whether it works

The required structure is short. Per the [APG Tree View Pattern](https://www.w3.org/WAI/ARIA/apg/patterns/treeview/), "All tree nodes are contained in or owned by an element with role tree". Every node is a `treeitem`. "Each parent node contains or owns an element with role group". Parents carry `aria-expanded`, and end nodes must not carry it, "because, if they were to have it, they would be incorrectly described to assistive technologies as parent nodes." The tree needs a name through `aria-labelledby` or `aria-label`. Multi-select trees set `aria-multiselectable="true"`. Selection is indicated by **either `aria-selected` or `aria-checked`, never both** in one tree. The APG recommends the common convention of `aria-selected` for single select and `aria-checked` for multi-select. It says a tree needing both is "extremely rare" and should be avoided. The ARIA 1.3 Editor's Draft (05 Nov 2026) tightens 1.2 in two ways. It drops "required" from treeitem `aria-selected` and makes `aria-level` a supported property of treeitem. It also states that authors "MAY use nested group elements to implicitly indicate level hierarchy. Otherwise, authors MUST ensure all treeitem elements in the tree have explicit values for aria-level, aria-posinset, and aria-setsize" ([WAI-ARIA 1.3 ED](https://w3c.github.io/aria/)). Unknown totals use `aria-setsize="-1"`.

The first detail that decides success is **declaring position, not computing it**. The APG's two File Directory examples differ only in whether the browser computes level and position from nested groups (1a) or the author declares them (1b). The APG warns that computation is permitted but not required, so some browser and AT pairs misreport. Its advice is to "override automatic computation by explicitly declaring their values" when testing reveals gaps ([APG treeview-1a](https://www.w3.org/WAI/ARIA/apg/patterns/treeview/examples/treeview-1a/); [APG Navigation Treeview](https://www.w3.org/WAI/ARIA/apg/patterns/treeview/examples/treeview-navigation/)). GitHub hit exactly this: "we needed to explicitly declare the level on each li element … This fix addressed multiple forms of assistive technology we tested with" ([GitHub Blog](https://github.blog/engineering/user-experience/considerations-for-making-a-tree-view-component-accessible/)). Declaration costs a server renderer nothing, because it already knows depth and sibling counts. Declared values are also mandatory once lazy loading leaves part of the tree out of the DOM.

The second detail is **implicit selection**. ARIA 1.3 lets a user agent imply `aria-selected="true"` on the focused treeitem when no item in a single-select tree declares `aria-selected` or `aria-checked` ([WAI-ARIA 1.3 ED](https://w3c.github.io/aria/)). A selectable tree whose selection does not follow focus should therefore write `aria-selected="false"` explicitly on every selectable item. A tree with no selection, used purely for navigation, should rely on `aria-current` and not on implied selection. The spec separates the two: "aria-current="page" can be used in a navigation tree to indicate which page is currently displayed, while aria-selected="true" indicates which page will be displayed if the user activates the treeitem."

The third detail is **one focus target per node**. `treeitem` is not a "children presentational" role in ARIA 1.2 or 1.3, so nesting is not forbidden normatively. In practice, though, the pattern assumes one tab stop and one focusable node. axe's `nested-interactive` rule describes focusable descendants of controls as "not announced by screen readers and create an empty tab stop" ([Deque axe nested-interactive](https://dequeuniversity.com/rules/axe/4.10/nested-interactive)). GitHub notes that tree views "were designed assuming a user will only ever navigate to a node and activate it" ([GitHub Blog](https://github.blog/engineering/user-experience/considerations-for-making-a-tree-view-component-accessible/)). Primer's guidelines forbid interactive elements besides the chevron ([Primer guidelines](https://primer.style/product/components/tree-view/guidelines/)). Fluent calls hover quick-actions "an unexpected pattern under WAI-ARIA treeview guidance" and requires a toolbar or menu equivalent ([Fluent 2 Tree usage](https://fluent2.microsoft.design/components/web/react/core/tree/usage)). For Autumn, that means no `<input>`, link or button inside an enhanced treeitem. Per-node actions belong in a toolbar outside the tree that acts on the focused or selected node, or in a later `treegrid` variant.

### The keyboard model, and what Autumn's core already covers

The APG vertical-tree keyboard model is fixed ([APG Tree View Pattern](https://www.w3.org/WAI/ARIA/apg/patterns/treeview/)). Down and Up move between visible nodes "without opening or closing a node". Right opens a closed node with focus staying put, moves to the first child of an open node, and does nothing on an end node. Left closes an open node, moves from a child to its parent, and does nothing on a closed root. Home and End go to the first and last visible node. Enter performs the default action, which in single-select trees where selection does not follow focus is "typically to select the focused node". Type-ahead is "recommended for all trees, especially for trees with more than 7 root nodes", and `*` optionally expands all siblings. Initial focus goes to the selected node, else the first node. In multi-select trees it goes to the first selected node. Multi-select has two models. The **recommended** model needs no held modifier: Space toggles, with optional Shift+Arrow, Shift+Space, Ctrl+Shift+Home/End and Ctrl+A. The **alternative** model uses Ctrl+Arrow to move without deselecting. The APG adds that separate "Select All" and "Unselect All" buttons "significantly improves accessibility". It calls selection following focus "very helpful in some circumstances" that "can severely degrade accessibility in others". The File Directory example keeps selection separate from focus, so users can explore without changing the viewer ([APG treeview-1a](https://www.w3.org/WAI/ARIA/apg/patterns/treeview/examples/treeview-1a/)). The APG says nothing about right-to-left. Mirroring Left and Right under `direction: rtl` follows desktop convention, but that is an inference, not APG text.

Autumn's keyboard core (`autumn/vendor/autumn-widgets.js`, contract in `docs/guide/keyboard.md`) already provides most of this. It has a document-level roving tabindex bound by `data-autumn-roving`, `[role=treeitem]` in its default item set, Home and End, typeahead, RTL swapping, and an initial tab stop on the item that is `aria-selected`, `aria-checked` or `aria-current`, which matches the APG initial-focus rule. Reading the code shows four gaps for trees. First, `listItems` skips only an item with **its own** `hidden` attribute. A treeitem inside a collapsed `ul role="group" hidden` is not itself hidden, so Down would land on invisible children and typeahead would match them. The APG examples skip descendants of closed nodes. Second, the core ignores any key pressed with Ctrl, so Ctrl+A and Ctrl+Space selection must come from pack code. Third, typeahead matches `el.textContent`. For an `li` treeitem that contains its child group, that text includes every descendant label, so the label must come first and icons must be CSS-only. Fourth, the core's active-descendant mode writes `aria-selected` on every move, which is selection-follows-focus. A tree must use roving mode.

The fix is a small, general change to the core: skip items with a `hidden` ancestor inside the list. That helps any nested roving list. The tree pack then adds a handler for Right, Left, `*`, Enter, Space and the Ctrl chords. It uses `data-autumn-orientation="vertical"` so the core leaves Left and Right alone, and calls `preventDefault` so the core's `defaultPrevented` check skips keys the pack has taken. The pack must also move the tab stop itself when a collapse hides the item that holds `tabindex="0"`. The APG states that focus must never fall to `<body>` ([APG Developing a Keyboard Interface](https://www.w3.org/WAI/ARIA/apg/practices/keyboard-interface/)).

## Screen-reader support is uneven, so navigation should not be a tree

There is no trustworthy support matrix. a11ysupport.io lists treeitem support as "unknown" ([a11ysupport.io treeitem](https://a11ysupport.io/tech/aria/treeitem_role)), and ARIA-AT has published no tree results. What exists is field evidence, and it points one way. Deque warns that support "is good in some screen readers, but poor in others, so the choice to implement an ARIA tree view should not be made lightly", and that arrow-key navigation is "less expected (at least for now) on the web" ([Deque University](https://dequeuniversity.com/library/aria/tree-view)). GitHub found that VoiceOver on macOS and iOS did not compute node names from complex row content, and fixed it with `aria-labelledby` pointing at each node's text span. It also found that roving tabindex "performed better than utilizing aria-activedescendant, which had issues with VoiceOver on macOS and iOS". Semantic `ul`/`li` helped low-end Android devices and Forced Colors heuristics ([GitHub Blog](https://github.blog/engineering/user-experience/considerations-for-making-a-tree-view-component-accessible/)). Sarah Higley adds that mobile screen readers "will essentially ignore aria-activedescendant" and that macOS VoiceOver ignores it "if you so much as look at it funny" ([Sarah Higley](https://sarahmhigley.com/writing/activedescendant/)). Older failures matter for structure. WebKit once failed to recognise a tree with `role="presentation"` elements in the chain ([WebKit 163763](https://bugs.webkit.org/show_bug.cgi?id=163763)). Christian Heilmann saw macOS VoiceOver announce the W3C tree demo as a table, while NVDA and Narrator worked ([Christian Heilmann](https://christianheilmann.com/?p=6869)).

Three implementation rules follow: roving focus only, an `aria-labelledby` label span on every item, and as few `role="none"` wrappers as possible. Nesting the group inside the `li role="treeitem"`, as APG 1a/1b and the ARIA spec's `aria-expanded` example do, satisfies the spec's request that an expandable treeitem be "the accessibility parent of the content it expands and collapses" ([WAI-ARIA 1.3 ED](https://w3c.github.io/aria/)). It needs no `aria-owns`. Primer's `li role="none"` > `div role="treeitem"` shape ([primer/view_components](https://raw.githubusercontent.com/primer/view_components/main/app/components/primer/alpha/tree_view.rb)) and the APG navigation example's `aria-owns` wiring both add the indirection that has broken AT before. Touch screen readers expand by double-tap, so the whole row must be a click target. WCAG 2.2 SC 2.5.8 sets a 24×24 CSS px minimum target size ([WCAG 2.2](https://www.w3.org/TR/WCAG22/#target-size-minimum)), and Primer requires the same 24×24 for nodes ([Primer accessibility](https://primer.style/product/components/tree-view/accessibility/)).

The case against `role="tree"` for navigation is unusually unanimous. The APG's own navigation-tree example says "the disclosure pattern is better suited for most web sites because few sites need the additional keyboard functionality required to support the ARIA tree role" ([APG Navigation Treeview](https://www.w3.org/WAI/ARIA/apg/patterns/treeview/examples/treeview-navigation/)). Primer calls the tree "not appropriate for global sidebar navigation". It says the tree "mirrors an operating system file explorer, not website navigation, which has a different mental model" and points to NavList instead ([Primer guidelines](https://primer.style/product/components/tree-view/guidelines/); [Primer accessibility](https://primer.style/product/components/tree-view/accessibility/)). Carbon rules it out for showing and hiding page content, for single-level nesting, and for primary product navigation ([Carbon usage](https://carbondesignsystem.com/components/tree-view/usage/)). Fluent rules it out for show/hide without hierarchy ([Fluent 2 Tree usage](https://fluent2.microsoft.design/components/web/react/core/tree/usage)). The APG disclosure-navigation alternative is a `nav` landmark with nested link lists and `<button aria-expanded aria-controls>` toggles, all in the Tab order. Arrow keys there "supplement, but do not replace, tabbing", and Escape closes fly-outs ([APG Disclosure Navigation](https://www.w3.org/WAI/ARIA/apg/patterns/disclosure/examples/disclosure-navigation/)). Adrian Roselli adds a hard rule from user testing: "Do not add aria-expanded to a link". The toggle must be a sibling button next to the section link ([Adrian Roselli](https://adrianroselli.com/2019/06/link-disclosure-widget-navigation.html)). A disclosure nav also keeps native link behaviour. GitHub had to re-implement "open in new tab" with Ctrl+Enter because "Nodes on tree view constructs are tree items, not links" ([GitHub Blog](https://github.blog/engineering/user-experience/considerations-for-making-a-tree-view-component-accessible/)).

Peer libraries split along the same line. React Aria 1.22 added a separate `NavigationTree` that drops selection entirely, renders a real link per row with `aria-current="page"`, and auto-reveals the current route's ancestors ([react-aria-components](https://www.npmjs.com/package/react-aria-components)). Angular Aria's `nav` mode swaps `aria-selected` for `aria-current` and stops calling `preventDefault`, so native links work ([@angular/aria](https://www.npmjs.com/package/@angular/aria)). An app-style link tree with `role="tree"` (IDE outline, docs explorer in a split pane) is legitimate. Fluent's "navigation" mode is master-detail, not page navigation. But it belongs as an opt-in mode of the selection tree in a later version, not as the default for sidebars.

Carbon offers 32px and 24px row densities ([Carbon usage](https://carbondesignsystem.com/components/tree-view/usage/)). Fluent indents 24px per level, 12px when compact ([Fluent 2](https://fluent2.microsoft.design/components/web/react/core/tree/usage)).

Three design lessons transfer to Autumn. First, the dominant state shape, a set of ids per concern plus one focused or current id, serializes directly into URLs and form fields. Second, **Zag's model is the easiest to compute on a server**: store checked leaf ids and derive branch state at render time ([@zag-js/tree-view](https://www.npmjs.com/package/@zag-js/tree-view)). Third, React Aria's choice of `treegrid` is a revealing outlier. It reuses GridList machinery so rows can hold expand buttons, checkboxes and drag handles. That buys valid interactive children at the cost of a grid-style keyboard model. No Adobe document states the rationale; it is read from source. Autumn should stay with plain `tree` and text-only rows in v1, and reserve `treegrid` for a future "rows with controls" variant. On cascade defaults the field splits. Ant, Mantine, Primer, Syncfusion and Fluent cascade by default with a strict opt-out, while MUI opts in per direction. The Primer Rails names `:descendants` and `:self` are the closest server-side precedent ([Primer ViewComponents](https://raw.githubusercontent.com/primer/view_components/main/app/components/primer/alpha/tree_view.rb)).

## A `<details>` baseline that the pack upgrades on `autumn:init`

A nested list of `<details>`/`<summary>` is the right JS-off baseline. It gives native disclosure, keyboard operation and server-renderable `open` state, and screen readers map `open` to expanded and collapsed ([MDN details](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/details); [Scott O'Hara](https://www.scottohara.me/blog/2022/09/12/details-summary.html)). It cannot carry tree roles. `<details>` permits "No `role`". Putting `role=button` on `<summary>` drops the expanded state in macOS Safari, and changing the role of `<details>` can stop `<summary>` exposing its role in Firefox. Links or inputs nested inside `<summary>` are handled inconsistently ([Scott O'Hara](https://www.scottohara.me/blog/2022/09/12/details-summary.html)). So the honest JS-off output is a nested disclosure list, which still announces "list" and nesting level in many screen readers. Interactive content, such as a node's checkbox or a "Show contents" fallback link, sits outside the `<summary>`. Leaves are plain `<li>` with text or a link, never an empty `<details>`. `<details name>` exclusive groups are document-scoped and make sense only as an opt-in "one open sibling" mode, with per-tree name prefixes. They are Baseline since September 2024 ([web-features](https://web-platform-dx.github.io/web-features-explorer/features/details-name)).

Without JS the server cannot see toggles, so open state comes from three server-side sources. The first is default-opening the ancestors of the current node, which is what Primer and React Aria NavigationTree do ([Primer TreeView React](https://primer.style/product/components/tree-view/)). The second is an explicit `?open=` id set carried by links. The third is the app's own persisted state. Expansion can animate with `::details-content`, Baseline since September 2025, from the external stylesheet only and inside `prefers-reduced-motion: no-preference` ([MDN ::details-content](https://developer.mozilla.org/en-US/docs/Web/CSS/::details-content)).

For the `tree` widget, the upgrade path is where Autumn's existing seam pays off. ADR 0030 specifies that the keyboard core "fires `autumn:init` on each new root, before roving set-up" (`docs/adr/0030-widget-plugin-seam.md`). The core guide says this exists "so plugin JS can set roles that roving reads". On that event, for each `[data-autumn-tree]` root, the pack script does the following. It sets `role="tree"` and `data-autumn-roving`. It turns each `li` that wraps a `<details>` into `role="treeitem"` with `aria-expanded` copied from `details.open`. It moves the label span and child `ul` out of the `<details>` and removes the empty element. It gives the child list `role="group"` and `hidden` when closed. It turns leaf `li`s into treeitems. Then roving initialises. Because the same hook fires for htmx swaps, lazily loaded fragments are upgraded by the same code. The upgrade must **move** nodes rather than clone them, and htmx attributes must live on the `ul`/`li`, never on `<details>`/`<summary>`. Otherwise htmx's bindings would be lost when the wrapper is removed.

The alternative is Primer's approach of server-rendering full ARIA tree markup and relying on JS for behaviour ([primer/view_components](https://raw.githubusercontent.com/primer/view_components/main/app/components/primer/alpha/tree_view.rb)). Autumn should reject it, because a `role="tree"` that arrives without its keyboard handler is a worse failure than an honest disclosure list. The cost of the upgrade approach is a brief re-layout at `DOMContentLoaded`. Matching CSS for both states keeps it to a role change rather than a visible jump.

The navigation widget needs no upgrade. It is the disclosure list with links. In Roselli's pattern, a parent with its own page renders its link, with a sibling `<details>` or button toggling the sub-list. The current item carries `aria-current="page"` and its ancestors render `open`. Optional arrow-key support can come later, as the APG allows, as a supplement to Tab ([APG Disclosure Navigation](https://www.w3.org/WAI/ARIA/apg/patterns/disclosure/examples/disclosure-navigation/)).

## htmx lazy loading: swap into the group, never the focused node

No official htmx tree example exists. The idiomatic pieces are htmx's lazy-load pattern ([htmx lazy-load](https://htmx.org/examples/lazy-load/)) and the `once` trigger modifier, which "will only trigger once" ([htmx hx-trigger](https://htmx.org/attributes/hx-trigger/)). In the baseline, a lazy closed node's `<details>` body holds a placeholder `li` with a real link, `?open=…#node-id`. JS-off users reload with that node open and its children rendered inline. In enhanced mode the `<details>` is gone, so the trigger is a pack event. The child `ul` carries `hx-get="/…/children?node=47" hx-trigger="autumn:tree-expand once" hx-swap="innerHTML"`. The pack dispatches `autumn:tree-expand` on the group the first time it opens a lazy branch. One endpoint serves both transports, returning a fragment when `HX-Request` is present and a full page otherwise. The notes did not verify whether htmx can listen to the non-bubbling `toggle` event, and this design does not need it.

Three of these mechanics follow from the APG and GitHub sources, and the fourth (error handling) follows Primer. The swap targets the **child group's inner HTML**, never `outerHTML` on the treeitem that holds focus. While loading, the group gets `aria-busy="true"`, which lets AT batch the changes ([WAI-ARIA 1.3 ED](https://w3c.github.io/aria/)). A polite live region says "Loading…" (WCAG 4.1.3). Focus stays on the parent. GitHub's rules cover the edge cases. If focus sat on a loading placeholder, move it to the first child when content arrives. If the branch turns out empty, return focus to the parent and **remove its `aria-expanded`**, because it is now an end node ([GitHub Blog](https://github.blog/engineering/user-experience/considerations-for-making-a-tree-view-component-accessible/)). Under APG semantics a second Right press then enters the new children naturally. Primer puts load errors in a dialog. Dismiss returns focus to the collapsed parent, and retry moves focus to the loading node ([Primer guidelines](https://primer.style/product/components/tree-view/guidelines/)). For a server-rendered widget, a simpler choice is an error `li` with a retry link that re-issues the GET. `once` has already fired, so the retry needs a fresh element. Fragments must render `aria-level`, `aria-setsize` and `aria-posinset` on every item, because they are inserted into an incomplete DOM. Using `once` also gives per-page caching: children stay in the DOM after collapse, the same model as Web Awesome's "lazy until content changes, then `lazy=false`" ([Web Awesome tree](https://webawesome.com/docs/components/tree)).

For large trees, the field's answer is lazy-on-expand, not virtualization. Primer, Web Awesome and Wijmo all rely on it ([Wijmo](https://developer.mescius.com/wijmo/docs/Topics/Nav/TreeView/DataBinding/Lazy-Loading.md)). Virtualization is a paid tier in MUI ([MUI X](https://mui.com/x/react-tree-view/)), bring-your-own in Mantine ([Mantine](https://mantine.dev/core/tree/)), and only kicks in with a fixed `height` in Ant ([Ant Tree](https://ant.design/components/tree)). A server-rendered tree should add per-level pagination. It renders up to N children (for example 100) and then a "Load 100 more of 1,203" row. That row swaps itself `outerHTML` for the next keyset page plus a new "more" row, and falls back to a plain link. Every real item declares `aria-setsize` as the true total, so AT says "5 of 1,203" while 100 are present. The "more" row is excluded from the count. Virtualization would flatten the DOM, defeat find-in-page and typeahead over unrendered rows, and risk destroying the focused row. It should stay out of v1. Two caveats apply. The notes found no measured DOM-size threshold for trees, so any budget number is a heuristic to tune. Typeahead only searches loaded nodes, which matters once paging exists.

## Form binding: native inputs as truth, tri-state computed on the server

The no-JS form story is native HTML. Same-name checkboxes submit as repeated values (`folders=3&folders=7`), and unchecked boxes submit nothing ([MDN checkbox](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/input/checkbox)). The form therefore needs a presence sentinel (`<input type=hidden name="folders_present" value="1">`) to tell "none selected" from "field absent". A single-select tree is a radio group with one `name`. Checkbox `indeterminate` "cannot be set using an HTML attribute" and "is purely a visual change" ([MDN checkbox](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/input/checkbox)). So without JS, the mixed state is server-computed and rendered as an `is-mixed` class drawn by CSS plus visually hidden text such as "(3 of 8 selected)". Server derivation follows the standard rule shared by Zag, MUI, Mantine and Primer. A parent is true if all selectable descendants are checked, false if none are, and mixed otherwise. Disabled descendants are excluded ([@zag-js/tree-view](https://www.npmjs.com/package/@zag-js/tree-view); [MUI Selection](https://mui.com/x/react-tree-view/rich-tree-view/selection/)).

Cascading cannot happen in the browser without JS, so **the server normalizes on submit**. Under a `Descendants` policy a submitted parent id expands to all its descendants, and branch state is re-derived on re-render. Under `Independent`, the equivalent of Primer's `:self` and Ant and Mantine's `checkStrictly`, each id stands alone ([Ant Tree](https://ant.design/components/tree); [Mantine Tree](https://mantine.dev/core/tree/)). A checked parent whose children were never loaded can only mean "all descendants", whatever the policy. headless-tree makes the same point client-side: propagation with an async loader "will recursively load descendants" ([@headless-tree/core](https://www.npmjs.com/package/@headless-tree/core)). Every submitted value is an opaque id, never a label, and is validated against the subtree the user is authorised to see.

In enhanced mode, the APG model for a checkbox tree is `aria-multiselectable="true"` with `aria-checked` on each treeitem, not a nested focusable checkbox. Whether `aria-checked="mixed"` is valid on `treeitem` is an open spec question: [w3c/aria #1640](https://github.com/w3c/aria/issues/1640) has been open since November 2021, and nobody has published support data. The pragmatic answer is to emit `mixed` on partly checked parents and keep the count text as an `aria-describedby` fallback. The upgrade keeps each native checkbox in the DOM with the `hidden` attribute. Under HTML form rules a hidden but enabled checked checkbox still submits; this is an inference that needs a browser test. The pack toggles `input.checked` and `aria-checked` together, so the form never depends on a second, script-maintained copy of the state. Radios in a single-select tree get the same treatment, since native radio arrow keys would otherwise cross tree levels in DOM order. Autumn's `FieldControl::Custom` seam lets a pack own the control while the framework writes the label, hint and errors (`docs/adr/0030-widget-plugin-seam.md`), so the tree can be a first-class form field.

## CSP and security: escape labels, allow-list hrefs, bound the walk

Strict CSP constrains the tree's styling and scripting. **Indentation must come from nesting**, for example `.autumn-tree [role=group], .autumn-tree-children { padding-inline-start: var(--autumn-tree-indent) }`. Depth then compounds with no per-node attribute. Never emit `style="--depth:N"`: it is an inline style and fails `style-src` without `'unsafe-inline'`. Web Awesome's design exposes indentation through custom properties, yet its own docs example uses an inline `style=` ([Web Awesome tree](https://webawesome.com/docs/components/tree)). Guide lines come from `border-inline-start` on groups. The chevron rotation keys off `[aria-expanded="true"]` in enhanced mode and `details[open]` in the baseline. The loading indicator is styled from the stylesheet through htmx's request class.

On the htmx side, framework-emitted markup must not use `hx-on`, which is an inline handler, or `hx-trigger` filter expressions in brackets. The `once` modifier needs neither. The research notes say, without a verified source, that htmx compiles filter expressions with `Function()`, which needs `'unsafe-eval'`, and that indicator-style injection should be turned off under a strict `style-src`. Both should be checked against htmx's config docs. Autumn's own rule applies cleanly here: an app may pass `hx-on` explicitly, and ADR 0030 already has `FieldContext::control` drop `on*` and `style` from framework-owned attributes.

The remaining risks are ordinary but specific to trees. Labels are untrusted text rendered through maud's escaping. Rich labels come only through an explicit app-supplied `Markup` slot. Link nodes take a typed URL with a scheme allow-list of relative paths, `http`, `https` and `mailto`, with any unsafe scheme behind an explicitly named opt-in. Primer identifies lazy nodes by a JSON array of labels in the query string ([primer/view_components](https://raw.githubusercontent.com/primer/view_components/main/app/components/primer/alpha/tree_view.rb)). Autumn should use opaque, URL-encoded ids instead, and **authorise every children request**, because lazy endpoints are enumerable. Rendering a user-shaped hierarchy recursively risks stack exhaustion and runaway output, and a `parent_id` graph from a database can contain cycles. The renderer should therefore walk iteratively or enforce `max_depth` (32–64) and `max_nodes`. Past either budget it emits a lazy placeholder, and it keeps a visited set. Primer independently advises reconsidering a tree that users routinely navigate more than 10 levels deep ([Primer guidelines](https://primer.style/product/components/tree-view/guidelines/)). Finally, every `id`, `aria-labelledby` target, radio and checkbox `name`, `<details name>` and `hx-target` must be prefixed per tree instance (`{tree}-n{node}`). Node keys are mapped to `[A-Za-z0-9_-]` so they are safe in CSS selectors, or relative htmx targets are used to avoid global ids.

## Recommended v1: two widgets, one data model

The first version should ship the features every serious peer treats as baseline, and defer the outliers.

| Area | v1 | Deferred |
|---|---|---|
| Widgets | `nav_tree` (core, disclosure, links, `aria-current`) and `tree` (widget pack, APG upgrade) | `role=tree` link mode; `treegrid` rows with controls |
| Selection | `None`, `Single` (radio baseline → `aria-selected`, Enter/Space selects, no selection-follows-focus), `Multiple` checkbox (`aria-checked` true/false/mixed) | Leaf-only modes; selection-follows-focus opt-in; Shift range chords |
| Cascade | `Descendants` (default) and `Independent`; server-side normalization and tri-state derivation | Submit shapes (leaves only / collapsed parents) |
| Keyboard | Full APG single-select model plus Space toggle, Ctrl+A, `*`, typeahead skipping closed branches, RTL mirroring; visible Select all / Clear buttons | Shift+Space, Ctrl+Shift+Home/End |
| Lazy | `Children::Lazy { url, count }`, htmx fragment into the group, `aria-busy`, live-region status, error row with retry, `?open=` fallback | Reload-on-every-expand |
| Scale | Per-level keyset paging with a "load more" row; `max_depth`/`max_nodes` budgets | Virtualization |
| Visual | Whole-row 24px+ targets, 24px/12px indent tokens, two densities, optional guide lines, non-colour current/selected marker | Rename, DnD, inline actions |

A Rust shape that fits the evidence is a nested node type with a lazy variant, plus id-set state, mirroring the dominant peer model.

```rust
pub struct TreeNode {
    pub id: TreeKey,               // opaque, mapped to [A-Za-z0-9_-]
    pub label: String,             // escaped; rich labels via an explicit Markup slot
    pub href: Option<SafeHref>,    // scheme allow-listed; Href::unchecked is the named opt-in
    pub disabled: bool,
    pub children: Children,
}
pub enum Children { Leaf, Loaded(Vec<TreeNode>), Lazy { url: String, count: Option<u32> } }
pub enum TreeSelect { None, Single { name: String }, Multiple { name: String, cascade: Cascade } }
pub enum Cascade { Descendants, Independent }
pub struct TreeState { pub expanded: HashSet<TreeKey>, pub checked: HashSet<TreeKey>, pub current: Option<TreeKey> }
```

## Conclusion

The research turns a design question into a sequencing question. The ARIA tree pattern is stable and well understood, and every credible peer implements nearly the same state model. The real risk lies in the gap between that pattern and what assistive technology does with it. Autumn's constraints, server rendering, no-JS operation and a strict CSP, therefore push toward the same choices the most careful implementers reached empirically: a disclosure list as the honest default, an ARIA tree only where arrow-key exploration earns its cost, declared rather than computed structure, and server-owned state. The `autumn:init`-before-roving hook in ADR 0030 makes the "render a disclosure, upgrade to a tree" strategy cheap for Autumn in a way it is not for client-rendered libraries. The one core change it needs, skipping items under a hidden ancestor, improves every nested roving list.

What remains unknown should shape testing rather than delay the build. No one has published per-screen-reader results for declared-level trees, `aria-checked="mixed"` on treeitems, or `aria-busy` on groups. The widget-pack browser gate should therefore carry explicit NVDA, JAWS and VoiceOver manual checks for those three behaviours, not just axe and keyboard checks. Its findings would be among the first public evidence on them.
